The Case for Single-Pass Instance-Optimal Join Algorithms (When Storage Is Cheap)

Created on October 22, 2026 by Mihail Stoian

2026

With the rise of worst-case optimal joins in 2012, the database community has witnessed an increasing (re-)interest in optimizing the execution of join queries, both from research (Umbra, Predicate Transfer, Robust Predicate Transfer, Yannakakis+, Lookup & Expand, RPT++) and industry systems (e.g., SQL Server’s dissection). These algorithms are commonly referred to as instance-optimal algorithms. The field itself is not new, having originated with Yannakakis’ algorithm in 1981.

Why Yannakakis’ Was Not Enough

While the theoretical results are very promising, there is one recurrent issue that seems to dominate the community discussions: even today, the default Yannakakis’ algorithm hasn’t seen adoption in production. Instead, a rather more primitive form has seen wide adoption, even in production systems: the Bloom join - others refer to it as sideways information passing (SIP) or semi-join filtering. Upon closer inspection, it’s somehow clear that the Bloom join has made it into production, as it preserves the single-pass behavior of query execution, i.e., it doesn’t require additional passes over the tables: (i) construct hash tables on the build sides of the joins, and (ii) probe into these hash tables. Concretely, the Bloom filter pushed down to the probe side removes dangling tuples, i.e., tuples that will anyway not survive later joins. We decided to refer throughout the paper to this technique as probe-side filtering (PSF), as it’s always the probe side which is filtered (and the way it’s filtered doesn’t have to be through an exact semi-join).

Unlike PSF, Yannakakis’ algorithm requires multiple passes over the data, making query execution rather intricate. That is the reason why DuckDB refused to merge RPT’s pull request – an Yannakakis-inspired (instance-optimal) algorithm that removes the dangling tuples so that the final pass is executed on tables whose tuples will survive all joins in the plan. What PSF is essentially missing is the backward information flow present in instance-optimal algorithms. Namely, PSF induces only an upwards information flow (we formalize the information flow in Sec. 2.4).

🪂 Parachute

In Parachute (Stoian et al., 2025), we propose to enable the downwards information flow by pre-processing join-induced fingerprints, which are stored on foreign-key (FK) tables and are used during query execution to filter out dangling tuples. Doing this naively, however, results in overhead in both space and runtime. That’s why our fingerprints are lightweight, allowing for blazingly fast checks of whether a tuple is dangling or not. We support both numeric columns and, more importantly, string columns. For instance, for numeric data, we use histograms. On the JOB benchmark, this results in a 1.24x speedup over PSF-enabled DuckDB.

Let’s see how Parachute works at query execution time. Assume our system supports PSF by default. In the query $Q$, there is a filter predicate on table $T$. There are three steps to enable the information flow’s upwards direction: (A) We take the query plan of query $Q$, as output by the system’s query optimizer. (B) We run an information-flow analysis which identifies the pairs of tables between which information flow is blocked. Since PSF induces an upwards flow, we see that there’s no flow from $T$ to $S$, i.e., ᄀ ($T$ ⇝ $S$). This is where Parachute comes in. In (C), using the already pre-computed fingerprint columns in the database, it drops the parachute predicate on $S$, unblocking the downwards information flow, and, along with the already available upwards flow, it enables a bi-directional flow, similar to instance-optimal algorithms.

Fingerprints

How to build the fingerprint columns? In the current version, these are built during a pre-processing step, e.g., at data loading time. The next figure visualizes this step. Given the FK-table cast_info we consider the non-key column year from table title. We attach the fingerprint column corresponding to year by performing the join with title and storing a lightweight representation (lossy) representation of the column. To this end, we use a histogram – for instance, the year value 2025 is mapped to histogram bin 3. That’s why both tuples with cast_info.movie_id = 789 have the value of 3 in the attached fingerprint column.

We can see that attaching a parachute of a column is equivalent to denormalizing a table, yet with a lossy representation of the FK-induced columns. The loading phase is surely the most expensive, yet we show that for large workloads, this overhead amortizes.

Results

We evaluated Parachute on the JOB and CEB benchmarks. On JOB, the speedup on the vanilla DuckDB is 1.54x (parachute[duckdb + psf]), whereas if we enable PSF only, the speedup is 1.24x (duckdb + psf). We can also inspect the number of dangling tuples left on the base tables, namely we achieve a reduction of 8.79x and 2.38x in the total number of dangling tuples over vanilla DuckDB and DuckDB with PSF, respectively. (On the 13k-query CEB, the speedup is similar.) Note that these results are using 16-bit fingerprints, which take up to +15% storage overhead over the original database size. Podcast

We’re delighted that we could take about Parachute on the Disseminate: The Computer Science Research Podcast. Given its framework-like style, Parachute is a lightweight mechanism to boost one’s join-heavy workloads, without having to modify the query engine.

Future Work

Motivated by the rather intriguing property of string fingerprints to act as a false-positive LIKE evaluation, we optimized them to the workload – this resulted in Instance-Optimized String Fingerprints (Stoian et al., 2025). We plan to bring this workload optimization into all column types. A great feature of fingerprint columns is that they can be (implicitly) used for file skipping, resulting in join pruning! We’re preparing a DuckDB extension that can be used by database practitioners to boost their query workloads without changing DuckDB’s internals.
